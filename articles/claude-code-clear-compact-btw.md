## はじめに

Claude Code で作業していて、こんな経験はありませんか？

> 「そこじゃない、直して」→「修正しました！」→「……まだ同じミスしてる」→「修正しました！」

2回、3回と直してもらうほど、むしろ悪くなっていく。粘ってもう1回だけ……と続けて、気づけば30分経っている。

先日 Instagram（[@k_grid_blog](https://www.instagram.com/k_grid_blog/)）で、この悩みへの答えを約60秒のリールにしました。この記事はその解説版です。リールでは入りきらなかった「なぜそうなるのか」と「具体的にどう書くか」まで掘り下げます。

この記事で分かること

- 同じミスが続くとき、修正を重ねるより `/clear` でやり直した方が速い理由
- やり直すときにプロンプトに足す「1文」の書き方
- 作業が変わったときに会話を区切る理由
- `/compact` に「何を残すか」を指示して要約する方法
- 履歴に残さずに質問できる `/btw` の使いどころ
- 要約で消えてほしくない情報を CLAUDE.md に書いておく方法

:::message
コンテキスト管理シリーズの3本目です。1本目は「AIの記憶をどこに置くか（Obsidian）」、2本目は「CLAUDE.md に書くこと・書かないこと」でした。今回は**作業中の会話そのもの**の管理の話です。
:::

## 前提：コンテキストは「たまるほど性能が落ちる」

Claude Code の公式ドキュメント（Best practices）では、ほとんどのベストプラクティスの土台にあるのは次の制約だ、と説明されています。

> Claude's context window fills up fast, and performance degrades as it fills.
> （コンテキストウィンドウはすぐに埋まり、埋まるほど性能が落ちる）

コンテキストウィンドウには、会話のすべてが入ります。自分のメッセージ、Claude の返答、読み込んだファイル、実行したコマンドの出力などです。これが埋まってくると、Claude は前のほうの指示を「忘れ」始めたり、ミスが増えたりします。

つまり、**会話は長くなるほど性能が落ちていく資源**です。今回紹介するコマンドは、どれもこの資源を「掃除」するための道具です。

| コマンド | すること | 使う場面 |
|---|---|---|
| `/clear` | 会話を全部消してまっさらにする | 同じミスが続いた／作業が変わった |
| `/compact` | 会話を要約して縮める | 同じ作業を続けたいが、会話が長くなった |
| `/btw` | 履歴に残さずに質問する | 今の作業についてちょっと確認したい |

## 1. 2回直してダメなら `/clear`

### なぜ直すほど悪化するのか

修正をお願いするたびに、コンテキストには次のようなものがたまっていきます。

```text
最初の指示
✗ 失敗①（間違ったコード）
修正の指示
✗ 失敗②（また間違ったコード）
修正の指示
...
```

失敗したコードも、それに対する指摘も、全部が会話の一部として残ります。Claude は次の返答を作るときにこれらを全部読むので、**失敗したやり方そのものが「参考資料」になってしまう**わけです。

公式ドキュメントにも、はっきりこう書かれています。

> If you've corrected Claude more than twice on the same issue in one session, the context is cluttered with failed approaches. Run `/clear` and start fresh with a more specific prompt that incorporates what you learned.

要約すると、「同じ問題を2回より多く直しているなら、コンテキストは失敗したやり方で散らかっている。`/clear` して、学んだことを入れたもっと具体的なプロンプトでやり直そう」ということです。続けて「きれいなセッション＋良いプロンプトは、修正を積み重ねた長いセッションに、ほぼ必ず勝つ」とも書かれています。

「よくある失敗パターン」の一覧にも、**Correcting over and over（何度も直し続ける）** が載っています。対策は「2回修正に失敗したら `/clear` して、学んだことを入れた最初のプロンプトを書き直す」です。

### 判断基準

迷ったら、これだけ覚えておけばOKです。

:::message
**同じ指摘を2回して直らなかったら、3回目は言わずに `/clear`。**
:::

## 2. やり直しのコツ：学んだことを「1文」足す

`/clear` しただけで最初と同じ指示を出すと、同じ失敗をもう一度たどる可能性があります。大事なのは、**2回の失敗で分かったことをプロンプトに足すこと**です。

たとえば、Next.js でログイン後のリダイレクトがうまくいかず、Claude が `useEffect` の中で `router.push` する修正を繰り返していたとします。

❌ やり直し前（最初の指示）

```text
ログインのリダイレクトを直して
```

✅ `/clear` してからのやり直し

```text
/clear
```

```text
ログインのリダイレクトを直して。
- ゴール：ログイン後は /dashboard へ戻す
- 場所：リダイレクトは middleware.ts で行う
- 使わない：useEffect での画面遷移は使わない（ちらつきが出たため）
```

足しているのは次の3つです。

| 足すもの | 例 | 役割 |
|---|---|---|
| ゴール | ログイン後は /dashboard へ戻す | 何ができたら完了かをはっきりさせる |
| 直す場所 | middleware.ts で行う | 探す範囲をしぼる |
| 使わないやり方 | useEffect での遷移は使わない | 同じ失敗の道に入らせない |

特に効くのが3つ目の**「使わないやり方」**です。2回の失敗は無駄ではなく、「このやり方はダメだった」という情報です。それを1文で渡すだけで、新しい会話でも同じ道を避けてくれます。

公式ドキュメントの「プロンプトで具体的に指示する」のセクションでも、症状・場所・「直った」の状態を書くことがすすめられています。

> "users report that login fails after session timeout. check the auth flow in src/auth/, especially token refresh. write a failing test that reproduces the issue, then fix it"

:::message
`/clear` を使うのが不安な場合は、`Esc` を2回押すか `/rewind` で巻き戻しメニューを開けば、前の時点の会話やコードに戻すこともできます。「やり直す」手段は1つではありません。
:::

## 3. 作業が変わったら `/clear` で区切る

同じミスが続いていなくても、`/clear` を使うべきタイミングがあります。**作業の種類が変わったとき**です。

```text
1つの会話の中で…
・ログイン修正
・（ついでに）このCSS、なんで崩れるの？
・（ついでに）APIの設計どうしよう
・（戻って）ログイン修正の続き
```

これは公式で **The kitchen sink session（何でも入れちゃうセッション）** と呼ばれている失敗パターンです。1つのタスクから始めて、関係ない質問をして、また最初のタスクに戻る。するとコンテキストは関係ない情報でいっぱいになります。

対策はシンプルで、「関係ないタスクの間で `/clear` する」です。

```text
会話①：ログイン修正
  ↓ /clear
会話②：CSSの質問
  ↓ /clear
会話③：API設計
```

ログイン修正をしているときに、CSSの話やAPI設計の話は必要ありません。関係ない情報が混ざるほど、Claude の注意が分散します。

:::message
後で戻りたい作業なら、`/rename` で会話に名前を付けておき、`claude --resume` で選んで再開できます。公式でも「セッションをブランチのように扱う」ことがすすめられています。
:::

## 4. 続けたいなら `/compact` で縮める

一方で、「同じ作業をまだ続けたいけど、会話が長くなってきた」という場面もあります。ここまでの経緯を全部消してしまうのはもったいない。そんなときは `/compact` です。

`/compact` は、会話の履歴を要約して縮めるコマンドです。ポイントは、**何を中心に残すかを指示できる**ことです。

```text
/compact APIの変更を中心に残して
```

公式ドキュメントの例は `/compact Focus on the API changes` です。何も指定しないより、「今の作業で大事なもの」を伝えた方が、要約の後も作業を続けやすくなります。

また、コンテキストの上限に近づくと、Claude Code は**自動でも会話を要約します**（auto compaction）。公式の説明では、このときコードのパターン、ファイルの状態、重要な決定などを優先して残してくれます。

| | `/clear` | `/compact` |
|---|---|---|
| すること | 会話を全部消す | 会話を要約して縮める |
| これまでの経緯 | 残らない | 要約されて残る |
| 向く状況 | 失敗が続いた／作業が変わった | 同じ作業で会話が長くなった |

:::message
会話の一部だけを要約したい場合は、`Esc` を2回押すか `/rewind` でメッセージを選び、**Summarize from here**（ここから後を要約）や **Summarize up to here**（ここまでを要約）を選ぶ方法もあります。
:::

## 5. ちょっとした確認は `/btw`

作業の途中で、「あれ、さっきの設定ファイルの名前なんだっけ？」と確認したくなることがあります。普通に聞くと、その質問と答えも会話の履歴に残り、コンテキストが少し増えます。

そんなときに使えるのが `/btw` です。

```text
/btw さっきの設定ファイル名なんだっけ？
```

公式ドキュメントの説明を整理すると、`/btw` には次の特徴があります。

- **質問と答えは会話の履歴に入らない**。なので、コンテキストを増やさずに確認できる
- Claude が作業中でも使える。メインの作業は止まらない
- **すでに会話にある情報だけで答える**。ファイルを読む、コマンドを実行する、検索するといったツールは使えない
- 1回の質問に1回の答え。続けて聞きたいときは、もう一度 `/btw` する
- 答えはターミナル上に重ねて表示され、閉じられる

:::message alert
`/btw` は「何でも聞ける別のチャット」ではありません。ツールを使えないので、まだ読んでいないファイルの中身などは答えられません。**今の作業について、会話にある内容を確認する**ためのコマンドと考えるのが正確です。
:::

使いどころの例です。

- 「さっき決めた方針、どっちだったっけ？」
- 「さっき読んだ関数の引数、何だった？」
- 「さっきのエラーメッセージ、もう1回見せて」

どれも、作業の流れを止めずに、会話を汚さずに確認できます。

## 6. 要約で消えてほしくないものは CLAUDE.md に書く

`/compact` や自動の要約は便利ですが、要約である以上、細かい情報は落ちることがあります。「これだけは絶対に残してほしい」というものがあるなら、**CLAUDE.md に要約のルールを書いておく**ことができます。

公式ドキュメントの例はこうです。

> "When compacting, always preserve the full list of modified files and any test commands"
> （要約するときは、変更したファイルの完全な一覧と、テストコマンドを必ず残すこと）

日本語で書くなら、たとえばこんな形です。

```markdown:CLAUDE.md
# Commands
- 型チェック: npm run typecheck

# Compact instructions
- 要約するときは、変更したファイルの一覧とテストコマンドを必ず残す
```

前回の記事で「CLAUDE.md には、消すとAIがミスする行だけを書く」という話をしました。「要約で何を残すか」は、まさに **消えるとAIがミスする情報** なので、CLAUDE.md に書く価値があります。

## まとめ

| チェック | やること |
|---|---|
| ✅ | 2回直してダメなら `/clear` |
| ✅ | やり直しは「ゴール・場所・使わないやり方」を1文で足す |
| ✅ | 作業が変わったら `/clear` で区切る |
| ✅ | 長くなったら `/compact` ＋ 何を残すかの指示 |
| ✅ | ちょっとした確認は `/btw`（履歴に残らない） |
| ✅ | 要約で残してほしいものは CLAUDE.md に書く |

AIが同じミスを繰り返すと、つい「もう1回だけ」と粘りたくなります。でも、会話にたまった失敗の跡がミスの原因になっていることも多いです。

**粘るより、やり直す。会話もこまめに掃除する。**

次に Claude Code が同じミスを2回したら、3回目を言う前に `/clear` を試してみてください。
