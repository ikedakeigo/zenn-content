## この記事でわかること

- 同じミスが続くとき、修正を重ねるより `/clear` でやり直した方が速い理由と、やり直すプロンプトの書き方
- `/clear`・`/compact`・`/btw` の使い分け
- 要約で消えてほしくない情報を CLAUDE.md に書いておく方法

Claude Code で作業していて、こんな経験はないでしょうか。

> 「そこじゃない、直して」→「修正しました！」→「……まだ同じミスしてる」→「修正しました！」

2回、3回と直してもらうほど、むしろ悪くなっていく。粘ってもう1回だけ……と続けて、気づけば30分経っている。この記事では、その原因と抜け出し方を、公式ドキュメントをもとに整理します。

## 前提

- 対象：Claude Code（ターミナル版の CLI）
- 仕様は 2026年10月18日時点の公式ドキュメントで確認しています。執筆時の手元のバージョンは 2.1.299 です
- 記事内の `/clear`・`/compact`・`/btw` の入力例は説明用の例です。実際の返答はプロジェクトや会話の内容によって変わります

## 全体像

最初に、なぜ「掃除」が必要なのかを押さえます。

Claude Code の公式ドキュメント（Best practices）は、ほとんどのベストプラクティスの土台にある制約を次のように説明しています。

> Claude's context window fills up fast, and performance degrades as it fills.
> （コンテキストウィンドウはすぐに埋まり、埋まるほど性能が落ちる）

コンテキストウィンドウ（Claude がその時点で参照できる情報の枠）には、会話のすべてが入ります。自分のメッセージ、Claude の返答、読み込んだファイル、実行したコマンドの出力などです。これが埋まってくると、Claude は前のほうの指示を「忘れ」始めたり、ミスが増えたりします。

つまり、**会話は長くなるほど性能が落ちていく資源**です。今回の3つのコマンドは、どれもこの資源を整理するための道具です。

| コマンド | すること | 使う場面 |
|---|---|---|
| `/clear` | コンテキストをリセットして新しい会話を始める | 同じミスが続いた／関係ないタスクに移る |
| `/compact` | 会話を要約して縮める | 同じ作業で会話が長くなった |
| `/btw` | メインの会話履歴に残さずに質問する | 今の作業についてちょっと確認したい |

:::message
`/clear` しても、それまでの会話が消えてなくなるわけではありません。前のセッションは保存されていて、`/resume` で再開できます。作業中のファイルもそのままです。新しい会話に**引き継がない**だけです。
:::

## 手順と使い分け

### 1. 2回直してダメなら `/clear`

修正をお願いするたびに、コンテキストには次のようなものがたまっていきます。

```text
最初の指示
✗ 失敗①（間違ったコード）
修正の指示
✗ 失敗②（また間違ったコード）
修正の指示
...
```

失敗したコードも、それに対する指摘も、全部が会話の一部として残ります。Claude は次の返答を作るときにこれらを全部読みます。そのため、**失敗したやり方そのものが「参考資料」になってしまう**のです。

公式ドキュメントにも、はっきりこう書かれています。

> If you've corrected Claude more than twice on the same issue in one session, the context is cluttered with failed approaches. Run `/clear` and start fresh with a more specific prompt that incorporates what you learned.

要約すると「同じ問題を2回より多く直しているなら、コンテキストは失敗したやり方で散らかっている。`/clear` して、学んだことを入れた具体的なプロンプトでやり直そう」という内容です。続けて「きれいなセッション＋良いプロンプトは、修正を積み重ねた長いセッションにほぼ必ず勝つ」とも書かれています。

「よくある失敗パターン」の一覧にも、**Correcting over and over（何度も直し続ける）** が載っています。対策は「2回修正に失敗したら `/clear` して、学んだことを入れた最初のプロンプトを書き直す」です。

:::message
**判断基準：同じ問題の修正を2回頼んでも直らなかったら、3回目を頼む前に `/clear`。**
:::

### 2. やり直すときは、学んだことを短く具体的に足す

`/clear` しただけで最初と同じ指示を出すと、同じ失敗をもう一度たどる可能性があります。大事なのは、**2回の失敗で分かったことをプロンプトに足すこと**です。

たとえば、Next.js でログイン後のリダイレクトがうまくいかず、Claude が `useEffect` の中で `router.push` する修正を繰り返していたとします。

最初の指示はこうでした。

```text
ログインのリダイレクトを直して
```

`/clear` してから、次のように出し直します。

```text
ログインのリダイレクトを直して。
- ゴール：ログイン後は /dashboard へ戻す
- 場所：リダイレクトは middleware.ts で行う
- 使わない：useEffect での画面遷移は使わない（ちらつきが出たため）
```

足しているのは次の3つです。

| 足すもの | 例 | 役割 |
|---|---|---|
| ゴール | ログイン後は /dashboard へ戻す | 何ができたら完了かをはっきりさせる |
| 直す場所 | middleware.ts で行う | 探す範囲をしぼる |
| 避けたいやり方 | useEffect での遷移は使わない | 同じ失敗の道に入らせない |

特に効くのが3つ目の**「避けたいやり方」**です。2回の失敗は無駄ではなく、「このやり方はダメだった」という情報です。それを短く書き足すだけで、新しい会話でも同じ道を避けてくれます。

公式ドキュメントのプロンプトの例でも、症状・場所・「直った」の状態を書くことがすすめられています。

> "users report that login fails after session timeout. check the auth flow in src/auth/, especially token refresh. write a failing test that reproduces the issue, then fix it"

:::message
`/clear` を使うのが不安なときは、**入力欄が空の状態で** `Esc` を2回押すか、`/rewind` を実行して巻き戻しメニューを開く方法もあります。チェックポイントに記録された時点の会話やコード変更に戻せます。ただし、Bash コマンドや外部ツールによる変更は巻き戻しの対象外です。
:::

### 3. 関係ないタスクに切り替えるときも `/clear`

同じミスが続いていなくても、`/clear` を使うべきタイミングがあります。**今の作業と関係ないタスクに切り替えるとき**です。

```text
1つの会話の中で…
・ログイン修正
・（ついでに）このCSS、なんで崩れるの？
・（ついでに）APIの設計どうしよう
・（戻って）ログイン修正の続き
```

これは公式で **The kitchen sink session（何でも入れちゃうセッション）** と呼ばれている失敗パターンです。1つのタスクから始めて、関係ない質問をして、また最初のタスクに戻る。するとコンテキストは関係ない情報でいっぱいになります。

対策は「関係ないタスクの間で `/clear` する」です。

```text
会話①：ログイン修正
  ↓ /clear
会話②：CSSの質問
  ↓ /clear
会話③：API設計
```

ログイン修正をしているときに、CSSやAPI設計の話は必要ありません。関係ない情報が混ざるほど、Claude の注意が分散します。

逆に、同じ機能の調査から実装、テストへと進むような**関連する作業**なら、それまでの経緯が役に立ちます。その場合は `/clear` せずに続け、長くなってきたら次の `/compact` を使います。

:::message
後で戻りたい作業なら、`/rename` で会話に名前を付けておくと、`claude --resume` で選んで再開しやすくなります。
:::

### 4. 同じ作業を続けるなら `/compact` で縮める

「同じ作業をまだ続けたいけど、会話が長くなってきた」という場面もあります。ここまでの経緯を手放すのはもったいないので、そんなときは `/compact` を使います。

`/compact` は、会話の履歴を要約して縮めるコマンドです。ポイントは、**何を中心に残すかを指示できる**ことです。

```text
/compact APIの変更を中心に残して
```

公式ドキュメントの例は `/compact Focus on the API changes` です。何も指定しないより、今の作業で大事なものを伝えた方が、要約の後も作業を続けやすくなります。

また、コンテキストの上限に近づくと、Claude Code は**自動でも会話を要約します**（auto compaction）。公式の説明では、このときコードのパターン、ファイルの状態、重要な決定などを優先して残します。

| | `/clear` | `/compact` |
|---|---|---|
| すること | コンテキストをリセット | 会話を要約して縮める |
| これまでの経緯 | 新しい会話に引き継がない | 要約されて残る |
| 向く状況 | 失敗が続いた／関係ないタスクに移る | 同じ作業で会話が長くなった |

:::message
会話の一部だけを要約したいときは、入力欄が空の状態で `Esc` を2回押すか `/rewind` を実行してメッセージを選びます。そこで **Summarize from here**（ここから後を要約）か **Summarize up to here**（ここまでを要約）を選べます。
:::

### 5. ちょっとした確認は `/btw`

作業の途中で「あれ、さっきの設定ファイルの名前なんだっけ？」と確認したくなることがあります。普通に聞くと、その質問と答えもメインの会話履歴に残り、コンテキストが少し増えます。

そんなときに使えるのが `/btw` です。

```text
/btw さっきの設定ファイル名なんだっけ？
```

公式ドキュメントの説明を整理すると、`/btw` には次の特徴があります。

- **質問と答えはメインの会話履歴に入らない**。そのため、コンテキストを増やさずに確認できる
- ただし、ターミナル版では直近20往復までの `/btw` のやりとりが、次の `/btw` の質問に引き継がれる（`x` キーで消せる）
- Claude が作業中でも使える。メインの作業は止まらない
- **すでに会話にある情報だけで答える**。ファイルを読む、コマンドを実行する、検索するといったツールは使えない
- 1回の質問に1回の答え。続けて聞きたいときは、もう一度 `/btw` する

:::message alert
`/btw` は「何でも聞ける別のチャット」ではありません。ツールを使えないので、まだ読んでいないファイルの中身などには答えられません。**今の作業について、会話にある内容を確認する**ためのコマンドです。
:::

使いどころの例です。

- 「さっき決めた方針、どっちだったっけ？」
- 「さっき読んだ関数の引数、何だった？」
- 「さっきのエラーメッセージ、もう1回見せて」

### 6. 要約で消えてほしくないものは CLAUDE.md に書く

`/compact` や自動の要約は便利ですが、要約である以上、細かい情報は落ちることがあります。必ず残してほしいものがあるなら、**CLAUDE.md（Claude Code が毎回読み込む指示ファイル）に要約のルールを書いておく**ことができます。

公式ドキュメントの例はこうです。

> "When compacting, always preserve the full list of modified files and any test commands"
> （要約するときは、変更したファイルの完全な一覧と、テストコマンドを必ず残すこと）

日本語で書くなら、たとえば次の形です。

```markdown:CLAUDE.md
# Commands
- 型チェック: npm run typecheck

# Compact instructions
- 要約するときは、変更したファイルの一覧とテストコマンドを必ず残す
```

シリーズの前回は「CLAUDE.md には、消すとAIがミスする行だけを書く」という話でした。要約で何を残すかは、まさに**消えるとAIがミスする情報**なので、CLAUDE.md に書く価値があります。

## まとめ

- 同じ問題の修正を2回頼んでも直らなかったら、`/clear` して「ゴール・場所・避けたいやり方」を足してやり直す
- 関係ないタスクに移るなら `/clear`、同じ作業で会話が長くなったら `/compact` ＋何を残すかの指示
- ちょっとした確認は `/btw`、要約で残してほしいものは CLAUDE.md に書く

AIが同じミスを繰り返すと、つい「もう1回だけ」と粘りたくなります。でも、会話にたまった失敗の跡がミスの原因になっていることも多いです。次に同じ問題の修正を2回頼んでも直らなかったら、3回目を頼む前に `/clear` を試してみてください。
